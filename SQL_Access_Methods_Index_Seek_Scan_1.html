Table Scan, Index Scan, Index Seek, and “Table Seek”

A beginner-friendly SQL Server tutorial using one Students table

Learning objectives: Explain how SQL Server finds rows, distinguish scans from seeks, recognize heap/table scans and clustered/nonclustered index access, inspect an execution plan, and understand why SQL Server may choose a scan even when an index exists.

1. One example for the entire tutorial

Imagine a college database with student records. Our goal is to find students by their StudentID or Major. SQL Server can read data in different ways depending on how the table is stored, which indexes exist, and how many rows the query needs.

2. First, what is a scan versus a seek?

Scan: SQL Server reads through a set of data pages or index entries, checking rows as needed. A scan can read all or part of a structure; it does not always mean every row is read.

Seek: SQL Server uses an index's search structure to navigate directly to a key or key range. A seek can still return many rows.

SCAN (read through entries): 101 → 102 → 103 → 104 → 105 SEEK (navigate using a searchable key): ↓ 101 102 [103] 104 105

Important: A seek is not automatically faster than a scan. If a query needs most of a table, sequential scanning may be more efficient.

3. Table Scan — searching a heap

A heap is a SQL Server table without a clustered index. A Table Scan operator reads heap data pages to locate rows.

CREATE TABLE dbo.StudentsHeap (
    StudentID INT NOT NULL,
    StudentName VARCHAR(50),
    Major VARCHAR(30)
);

INSERT INTO dbo.StudentsHeap VALUES
(101, 'Ana', 'CS'),
(102, 'Ben', 'Math'),
(103, 'Chen', 'CS'),
(104, 'Dia', 'Biology'),
(105, 'Eli', 'CS');

SELECT *
FROM dbo.StudentsHeap
WHERE StudentID = 103;

With no useful index, SQL Server cannot jump to StudentID 103 through an index. It may inspect heap rows and test StudentID = 103. In the execution plan, this typically appears as Table Scan.

Heap rows: [101] [102] [103] [104] [105] Check: no no YES no no
A heap's rows are not guaranteed to be physically ordered by StudentID. The sequence shown is conceptual, not a promise about physical storage.

What exactly is a heap?

A heap stores rows in no particular order. When a new row arrives, SQL Server places it on any data page that has free space, like putting books on a shelf in whatever gap you find. To find a row, SQL Server must either read every page (Table Scan) or use a nonclustered index that gives the row's address.

Is every normal table a heap? Only if it has no clustered index. Declaring a PRIMARY KEY creates a clustered index by default (unless you write PRIMARY KEY NONCLUSTERED or the table already has a clustered index). So most tables with a primary key are not heaps: their rows live in the clustered index's leaf pages.

4. Index Seek — navigating to matching keys

Now create a nonclustered index on StudentID. Think of the index as a searchable directory that maps StudentID values to the matching rows.

CREATE NONCLUSTERED INDEX IX_StudentsHeap_StudentID
ON dbo.StudentsHeap(StudentID);

SELECT *
FROM dbo.StudentsHeap
WHERE StudentID = 103;

SQL Server can use an Index Seek on the nonclustered index to locate key 103. Because SELECT * also needs StudentName and Major, SQL Server may additionally use a RID Lookup to fetch the remaining columns from the heap.

Nonclustered index (StudentID → row locator) 101 → row A 102 → row B 103 → row C ← seek here 104 → row D 105 → row E RID Lookup → fetch StudentName and Major for row C
For a tiny five-row table, SQL Server may still choose a Table Scan. An index makes a seek possible; it does not force one.

How a nonclustered index on a heap works

Creating the index does not move or sort the heap rows. SQL Server builds a separate B-tree that stores each StudentID in sorted order together with its RID (row identifier: the heap page and slot where the row lives). This matches the interactive lab above:

Root page: < 115 → Leaf 1 ≥ 115 → Leaf 2 (each boundary = the lowest key on that child page) Leaf 1: 101→RID 102→RID 105→RID 110→RID Leaf 2: 115→RID 120→RID 125→RID 130→RID (leaf pages are linked: Leaf 1 ⇄ Leaf 2) Heap (unordered): Page 1 [120, 101] Page 2 [130, 110] Page 3 [115, 105] Page 4 [125, 102]

Walkthrough: SELECT * FROM dbo.StudentsHeap WHERE StudentID = 120;

  1. Read the root page. 120 ≥ 115, so go to Leaf 2. Leaf 1 is never read.
  2. Read Leaf 2. Find key 120. Its RID says the row is on heap page 1.
  3. RID Lookup. Open heap page 1 and fetch StudentName and Major for SELECT *.

Result: 3 page reads instead of all 4 heap pages. In a real table with millions of rows, the root holds hundreds of boundaries and there may be one or two intermediate levels, yet a seek still reaches any key in about 3–4 page reads.

Analogy: the root page works like the guide words at the top of a dictionary page. You don't read every page; you check the range and jump.

Inside a leaf page

Keys inside a leaf page are sorted (115, 120, 125, 130), so SQL Server does not read them one by one. It uses a binary search within the page: check the middle, discard half, repeat.

If the index is not unique and 120 appears several times, all the 120 entries sit next to each other. SQL Server reads them in order and stops at the first key greater than 120 (here 125), because in sorted order no more 120s can follow.

What if duplicates span two leaf pages?

Suppose a non-unique index holds two rows with StudentID 120, and a page split left one at the end of Leaf 1 and the other at the start of Leaf 2:

Root page: < (120, RID 2:1) → Leaf 1 ≥ (120, RID 2:1) → Leaf 2 Leaf 1: 101 102 110 [120 → RID 1:3] Leaf 2: [120 → RID 2:1] 125 130

In a non-unique nonclustered index on a heap, SQL Server silently adds the RID to the key, so every entry, including each root boundary, is unique. For WHERE StudentID = 120:

  1. Root: SQL Server needs every 120, whatever its RID, so it starts from "120 + lowest possible RID". That is smaller than the boundary "120 + RID 2:1", so it goes to Leaf 1.
  2. Leaf 1: the last entry is 120. RID Lookup on heap page 1, slot 3.
  3. Next page: the leaf link leads to Leaf 2. Its first entry is 120, so it does another RID Lookup on page 2, slot 1.
  4. Stop: the next key is 125, greater than 120, so the search ends.

Result: both rows found with 3 index pages read (root, Leaf 1, Leaf 2) and 2 RID Lookups.

Key idea: a seek means jumping from the root to the correct starting point, then reading forward through linked leaf pages until the matching keys run out. This forward reading is called a range scan, and it is still part of the Index Seek operator.

When does SQL Server choose Index Seek?

A seek is possible whenever the key tells SQL Server where to start:

ScenarioExampleWhy a seek works
Exact valueWHERE StudentID = 115The root leads straight to one leaf page.
RangeWHERE StudentID BETWEEN 110 AND 125Seek to 110, read forward through linked leaves, stop after 125.
Leading column of a composite indexIndex on (Major, StudentID), WHERE Major = 'CS'Keys are sorted by Major first.
Prefix LIKEIndex on StudentName, WHERE StudentName LIKE 'An%'The beginning of the value is known.
One condition: the number of matching rows should be small. If a query returns a large fraction of the table, the many RID Lookups become expensive and the optimizer may choose a scan instead.

5. Index Scan — reading through an index

An Index Scan reads index entries rather than navigating directly to one narrow key range. For example, this query needs all indexed StudentID values:

SELECT StudentID
FROM dbo.StudentsHeap;

SQL Server may scan the smaller nonclustered index instead of the heap, because the index already contains every StudentID required.

Nonclustered index: [101] → [102] → [103] → [104] → [105] Read entries to produce all StudentIDs

An Index Scan can also occur with a filter on a column that is not a leading searchable key. For example, a StudentID index does not directly organize rows by Major.

SELECT StudentID
FROM dbo.StudentsHeap
WHERE Major = 'CS';

That query may use a Table Scan or another access path, depending on available indexes and costs. Do not assume it must use Index Scan.

How an Index Scan works

  1. Start: SQL Server goes to the first leaf page. It does not use the root to choose a key.
  2. Read Leaf 1: it reads 101, 102, 105 and 110, checking each entry against the condition.
  3. Next page: it follows the link to Leaf 2 and reads 115, 120, 125 and 130.
  4. End: it continues to the last leaf page, because nothing in the key order tells it that no more matches remain.
Analogy: an Index Seek jumps straight to the "S" section of a book's index. An Index Scan reads that index from top to bottom.

When does SQL Server choose Index Scan?

You do not pick the operator; the optimizer does. It scans when jumping to a starting point is impossible or pointless:

ScenarioExampleWhy no seek
All or most keys are neededSELECT StudentID FROM dbo.StudentsHeapEvery entry is needed anyway. The index is smaller than the table, so reading it is cheaper.
Function or expression on the columnWHERE StudentID + 0 = 115
WHERE YEAR(EnrollDate) = 2026		The index is sorted by the raw value, not the computed result, so every entry must be computed and checked.
Non-leading column of a composite indexIndex on (Major, StudentID), WHERE StudentID = 115Keys are sorted by Major first, so StudentID values are scattered.
Leading wildcardWHERE StudentName LIKE '%an'The beginning of the value is unknown, so there is no starting point.

Why? A seek works only when SQL Server knows where to start in key order. Consider an index on StudentName with the sorted names Ana, Ben, Chen, Dia, Eli, Jordan, Megan:

LIKE 'Me%' → seek straight to "Me" → Megan (Index Seek) LIKE '%an' → Ana? Ben? Chen? Dia? Eli? Jordan ✓ Megan ✓ (Index Scan) names ending in "an" could be anywhere in the list

Like a dictionary, the index is sorted by the first letters, not the last ones, so finding words that end in "an" means reading every entry.

Tip for students: write WHERE StudentID = 115, not WHERE StudentID + 0 = 115. Keep the indexed column alone on one side of the comparison so the optimizer can seek. Such a predicate is called SARGable (Search ARGument-able).

Index Scan + RID Lookup, and covering indexes

When a scan finds a matching entry and the query needs columns that are not in the index, SQL Server performs a RID Lookup for that row right away, then continues scanning. Rows flow one at a time; SQL Server does not collect all matches first. In the execution plan this appears as a Nested Loops join between the Index Scan and the RID Lookup.

If there are many matches, those lookups add up, and the optimizer usually prefers a plain Table Scan.

If the query selects only columns stored in the index, no lookup is needed at all. Such an index is called a covering index for that query. You can make an index cover extra columns with INCLUDE:

CREATE NONCLUSTERED INDEX IX_StudentsHeap_Name
ON dbo.StudentsHeap(StudentName) INCLUDE (Major);

-- Covered: no RID Lookup needed
SELECT StudentName, Major
FROM dbo.StudentsHeap
WHERE StudentName LIKE 'An%';

6. What about “Table Seek”?

SQL Server terminology: Table Seek is not a standard SQL Server graphical execution-plan operator. A heap can show Table Scan; a clustered index can show Clustered Index Seek; a nonclustered index can show Index Seek.

To demonstrate a seek against the table's clustered storage, create a second table with a clustered primary key:

CREATE TABLE dbo.StudentsClustered (
    StudentID INT NOT NULL PRIMARY KEY CLUSTERED,
    StudentName VARCHAR(50),
    Major VARCHAR(30)
);

INSERT INTO dbo.StudentsClustered VALUES
(101, 'Ana', 'CS'),
(102, 'Ben', 'Math'),
(103, 'Chen', 'CS'),
(104, 'Dia', 'Biology'),
(105, 'Eli', 'CS');

SELECT *
FROM dbo.StudentsClustered
WHERE StudentID = 103;

Because the table's rows are stored in a clustered index organized by StudentID key, SQL Server can use Clustered Index Seek to find StudentID 103. This is probably what someone informally means by “table seek.”

For SELECT * FROM dbo.StudentsClustered;, SQL Server will typically choose Clustered Index Scan, since it needs every row.

      The big difference: in a clustered table the whole row must be placed in StudentID order, and page splits physically move full rows. In a heap the row lands wherever there is space and keeps its RID; the ordering work happens only in the much smaller index. The trade-off: a clustered seek returns the full row directly, while the heap needs a RID Lookup for columns that are not in the index.
      What is simplified in this lab?

      Real pages are 8 KB and hold hundreds of rows. SQL Server finds heap free space using PFS (Page Free Space) pages, so after deletes a new row can land on an earlier page. When a page split happens at the end of an index (a new key larger than every existing key), SQL Server just adds a new page instead of splitting 50/50, which the lab also shows. The root page also has a limited size: when it fills, it splits and the tree grows one level, which the lab does not show. The initial indexes are built 100% full; a FILLFACTOR below 100 leaves free space and delays splits. In a table with a clustered index, nonclustered indexes store the clustering key instead of a RID. Updates that make a heap row larger can move it and leave a forwarding pointer at the old RID.

      9. How does the optimizer choose?

      SQL Server's query optimizer estimates the cost of alternative plans using statistics, row counts, selectivity, indexes, and expected I/O and CPU work. It selects a plan with a low estimated cost; it does not blindly use every available index.

      SQL query ↓ Optimizer considers possible access paths ├── Scan heap / clustered index ├── Scan nonclustered index └── Seek index (possibly followed by lookup) ↓ Chosen execution plan ↓ Rows returned

      Rule of thumb: A small number of matching rows often favors a seek. A large fraction of the table often favors a scan. The actual choice depends on the whole query.

      Does the root page know how many rows match?

      No. The root page stores only boundary keys and pointers to child pages, such as "below 115 → Leaf 1". It shows the way but does not count how many keys are below 115.

      Row-count estimates come from statistics. Each statistics object contains a histogram that records value ranges and roughly how many rows fall in each. The optimizer uses these estimates to decide between a seek and a scan.

      -- View the histogram for the StudentID index
DBCC SHOW_STATISTICS ('dbo.StudentsHeap', 'IX_StudentsHeap_StudentID');

      When do the root page boundaries change?

      SQL Server keeps the keys in order on every insert, update and delete. A key of 115 or more can never sit in Leaf 1 while the root says "below 115 → Leaf 1". The boundaries change only when the tree's structure changes:

      1. The page has room: the new key goes into its sorted position in the correct leaf, and the root stays the same. For example, if you delete 110 and insert 120, the 120 goes to Leaf 2, not Leaf 1.
      2. The page is full: a page split happens. The leaf is divided into two pages and a new boundary is added to the parent. If the root also fills up, it splits too and the tree grows one level taller.
      3. Deletes: SQL Server usually does not merge pages right away, so the boundaries stay. ALTER INDEX ... REORGANIZE compacts the leaf pages, and ALTER INDEX ... REBUILD recreates the tree with fresh boundaries.
      Statistics are separate. They are refreshed automatically when enough rows have changed (with the default AUTO_UPDATE_STATISTICS setting), when you run UPDATE STATISTICS dbo.StudentsHeap;, or when an index is rebuilt.

      10. Quick knowledge check

      Q1. A table has no clustered index and no other indexes. What operator is likely when searching for StudentID 103?
      Answer: Table Scan. SQL Server reads heap data pages because there is no index to navigate to that StudentID.
      Q2. We add an index on StudentID. Does SQL Server have to use Index Seek?
      Answer: No. The optimizer compares costs. A scan may be cheaper for a very small table or a query returning many rows.
      Q3. What is the difference between Index Scan and Index Seek?
      Answer: Index Scan reads through index entries; Index Seek navigates to selected key values or ranges. Neither is universally faster.
      Q4. What is the official SQL Server term for a seek on a table's clustered primary key?
      Answer: Clustered Index Seek. “Table Seek” is not the standard operator name.
      Q5. Why might Index Seek be followed by RID Lookup?
      Answer: A nonclustered index on a heap may identify the row without containing every column requested by SELECT *. The RID Lookup retrieves missing columns from the heap.
      Q6. You create a table with a PRIMARY KEY. Is it stored as a heap?
      Answer: Usually not. By default, a PRIMARY KEY creates a clustered index, so the rows are stored in the clustered index's leaf pages. A table is a heap only when it has no clustered index.
      Q7. Why can WHERE StudentName LIKE 'An%' use an Index Seek, but LIKE '%an' cannot?
      Answer: The index is sorted by the beginning of each name. 'An%' gives a known starting point; '%an' does not, so every entry must be checked with an Index Scan.
      Q8. Two entries for StudentID 120 sit at the end of Leaf 1 and the start of Leaf 2. How does an Index Seek find both?
      Answer: It seeks to the first 120 (in Leaf 1), reads forward through the linked leaf pages, and stops at the first key greater than 120 (125).
      Q9. Does the root page tell the optimizer how many rows have StudentID below 115?
      Answer: No. The root stores only boundaries and pointers. The optimizer estimates row counts from the statistics histogram.

      Key takeaway

      Scan means reading through data or index entries. Seek means using an index key to navigate to selected entries. A heap can have a Table Scan, a nonclustered index can have an Index Scan or Index Seek, and clustered table storage can have a Clustered Index Scan or Clustered Index Seek. The optimizer chooses based on estimated cost.
