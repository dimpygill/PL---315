Which x Does the Language Mean?

Where we left off: Chapter 3 asked what is a variable and how long does it exist? — binding, lifetime, name vs object. Now we ask the follow-up question: when a name appears in code, which variable does the language decide it refers to? That is scope.

Consider this Python program:

x = 100          # (A) — defined at the top level

def outer():
    x = 50       # (B) — defined inside outer()

    def inner():
        x = 10   # (C) — defined inside inner()
        print(x) # Which x does this print?

    inner()

outer()
🤔 Think First

Three variables all named x exist at the same time. When print(x) runs inside inner(), which one does Python use — (A), (B), or (C)? Write your prediction and your reasoning before reading on.

Answer: (C) — the value is 10.

Python looks up x starting in the innermost scope first. The name x exists locally in inner(), so that is what print(x) finds. Python never needs to look further.

But now change the question: what if we remove line (C) — the x = 10 inside inner()? Then Python would look in outer() next and find x = 50. Remove that too, and it finds x = 100 at the top level. This search order is the LEGB rule — and it is one of the most important things to understand about Python.

The deeper question: Why does Python use this particular search order? And why do C and C# structure scope differently? Those are the language design questions this chapter answers.

This chapter is about how languages resolve names. The problem sounds simple, but the design decisions behind it have real consequences for readability, correctness, and how easy it is to reason about code.

The conceptual flow of this chapter

Every time your code uses a name, the language must go through a chain of decisions. This chapter follows that chain:

Programmer writes a declaration
↓
Language defines scope rules — where that name is visible
↓
A name is referenced somewhere in the code
↓

↓

↓

🔧 Language Design Connection

The interesting question is not just how languages implement this — it is what design choices they made. Should names in inner scopes be allowed to shadow outer ones? Should nested functions see their enclosing function's variables? How much should the language protect programmers from accidental name conflicts?

C, C#, and Python each give different answers. By the end of this chapter you will be able to explain those differences and the tradeoffs behind them.

Section 1

What Is Scope?

In Chapter 3 we defined scope briefly and told you to keep it separate from lifetime. Now we go deeper.

Scope is the region of source code in which a name is visible and can be used.

Scope answers the question: where in the program can you write a name and have the language understand what you mean?

Scope is a textual property — not a runtime property

This is the most important thing to understand about scope upfront. Scope is determined by the structure of the source code — you can figure it out by reading the program, without running it. This is why it is often called lexical scope or static scope (we will return to this distinction in Section 2).

ConceptMain questionDetermined byExample
Scope Where can I use this name? Source code structure — readable without running the program "score is visible only inside greet()"
Lifetime How long does the object/value exist? Runtime — depends on when functions are called and return "score is created when greet() is called and destroyed when it returns"

Scope and lifetime are related but not the same thing. A classic example in C: a local variable declared with static has function scope (only visible inside the function) but program-long lifetime (persists across calls). The name goes out of scope when the function returns, but the object lives on.

The name resolution problem

Every time a program refers to a name, the language must resolve it — find which variable (or function, or type) that name refers to. Scope rules are the rules the language uses to do that resolution.

C — block scope

Names are visible from their declaration to the end of the enclosing block { }. No notion of class or module scope.

C# — four levels

Block → method → class → namespace. Each layer contains the next. A name can be visible at multiple levels simultaneously.

Python — LEGB

Local → Enclosing → Global → Built-in. Python searches outward through these four layers whenever it resolves a name.

🔧 Language Design Connection

What should happen when two scopes contain the same name? A language designer must answer this — and the answer determines how name resolution works, whether shadowing is allowed, and how deeply a function can "see" into its surrounding environment.

C, C#, and Python each draw different boundaries. Those differences are not accidents — they reflect deliberate choices about simplicity, safety, expressiveness, and implementation complexity. Sections 3–5 examine each language's choice in detail.

Section 2

Static Scoping vs Dynamic Scoping

Before examining the specific rules of C, C#, and Python, there is a fundamental language-design choice that underlies all of them: when are scope rules applied?

Static (Lexical) Scoping

The scope of a name is determined by its position in the source code — by the text of the program, as written. You can determine which variable a name refers to by reading the code, without running it.

Used by: C, C#, Python, Java, JavaScript, most modern languages.

Dynamic Scoping

The scope of a name is determined by the runtime call stack — which function called which. A name resolves to the most recently assigned value in the chain of callers, not in the textual structure of the code.

Used by: Early Lisp, Emacs Lisp, some shell scripting. Rare in modern languages.

Why the difference matters — a concrete example

-- Hypothetical: what DYNAMIC scoping would mean --
x = 1

def print_x():
    print(x)      # which x does this see?

def caller_a():
    x = 99
    print_x()     # dynamic: would see x=99 from caller_a's stack

def caller_b():
    x = 42
    print_x()     # dynamic: would see x=42 from caller_b's stack
Under static scoping (how Python actually works)
print_x()  # always prints 1
caller_a() # always prints 1
caller_b() # always prints 1
# x in print_x() is resolved
# by WHERE it is written —
# at the module level where x=1
Under dynamic scoping (hypothetical)
print_x()  # prints 1 (no caller's x)
caller_a() # prints 99 (caller_a's x)
caller_b() # prints 42 (caller_b's x)
# x in print_x() is resolved
# by WHO called it at runtime —
# unpredictable from reading code

Why most modern languages chose static scoping: With dynamic scoping, the meaning of a name depends on who called the function — you cannot understand the code by reading it alone. A function's behaviour can vary based on the call chain, making programs hard to reason about and hard for compilers to check at compile time.

Note on symbol tables: Symbol tables are useful for both static and dynamic scoping. Under static scoping, a compiler can build most of the symbol table from the source text alone. Under dynamic scoping, the language runtime still needs to track names and their values — but the lookup follows the call stack rather than the source structure. Static scoping makes compile-time analysis and error detection significantly easier.

🤔 Design Question

Can you think of a situation where dynamic scoping might actually be useful? What kind of program might benefit from a name resolving differently depending on who called the function?

Dynamic scoping has been used in configuration and environment systems — where you want a function to use the "current context's" settings without passing them explicitly. For example, a logging function that should use whatever log level is active in the current execution context.

But this same flexibility makes code hard to debug and maintain. Most modern language designers concluded that the predictability of static scoping outweighs the convenience of dynamic scoping. Python, C, and C# all use static (lexical) scoping.

All three of our languages — C, C#, and Python — use static (lexical) scoping. Their scope rules differ in the structure they define (blocks, functions, classes, namespaces, the LEGB rule), but all three resolve names based on the textual structure of the source code, not on the runtime call stack.

🔧 Language Design Connection

Choosing static scoping was a design decision with consequences: it makes programs more predictable and enables compilers to check names and types before the program runs. It also meant language designers had to specify exactly which textual structures create new scopes — blocks, functions, classes, modules — and in what order those scopes are searched. The next three sections show how C, Python, and C# each answered those questions.

Section 3

C: Block Scope, File Scope, and Three Keywords

C has a relatively simple scope model — three levels, determined entirely by where a declaration appears in the source code. This simplicity is itself a design choice: C's designers prioritised directness and programmer control over the kind of multi-level scoping that object-oriented languages later introduced.

The three levels of scope in C

Scope levelWhere the name is declaredVisibilityExample
Block scope Inside a pair of { } From declaration to the closing } Local variables in a function, variables in an if block
Function scope Labels only (for goto) Entire function body start: in a goto start; statement
File scope Outside any function From declaration to end of file Global variables, functions defined at the top level

Block scope — the common case

#include <stdio.h>

int globalScore = 0;    // file scope — visible everywhere in this file

void process(int n) {   // n has block scope: the function body
    int result = n * 2;  // block scope: visible from here to the }

    if (result > 10) {
        int bonus = 5;   // block scope: visible only inside this if-block
        result += bonus;
    }

    // bonus is NOT visible here — its block has ended
    printf("%d\n", result);
}

The static keyword — extending or restricting scope

C's static keyword does two different things depending on where it is used — a notorious source of confusion for new C programmers:

static on a local variable — extended lifetime, same scope
void counter() {
    static int count = 0;
    count++;
    printf("%d\n", count);
}
// count is still only visible inside counter()
// but persists across calls: 1, 2, 3, 4 ...
static on a file-scope variable — restricted to this file
// file: helper.c
static int internalCount = 0;
// internalCount is NOT visible to other .c files
// even though it's at file scope
// This is C's version of "private"

Same keyword, two meanings: static on a local variable means "preserve this variable's value across function calls" (affects lifetime, not scope). static on a file-scope variable or function means "don't make this visible to other files" (restricts scope). This overloading of one keyword is widely considered a C design flaw — C++ and other languages provide separate mechanisms for each.

The extern keyword — reaching across files

main.c
extern int sharedCount;
// "sharedCount is defined somewhere else"
// This declaration lets this file use it

int main() {
    sharedCount++;
    return 0;
}
counter.c
int sharedCount = 0;
// The actual definition lives here.
// Any other file that uses "extern"
// can access this variable.

C has no notion of class scope or namespace scope — these were additions made by C++ and later languages. In C, multi-file organisation relies entirely on static (to hide) and extern (to share), which are powerful but require careful discipline.

Name resolution in action — C's rule

When the compiler encounters a name in C, it searches outward through nested scopes until it finds a matching declaration. The first match wins. Consider this example, which demonstrates shadowing across three levels:

int x = 10;       // file scope

int main() {
    int x = 20;   // shadows the file-scope x

    {
        int x = 30; // shadows main()'s x
        printf("%d", x); // (1) → 30: innermost x wins
    }

    printf("%d", x); // (2) → 20: inner block ended, main()'s x is visible
}
Resolving x at (1):
Look in innermost block → found: x = 30 ✓ stop here

Resolving x at (2):
Inner block ended — its x is gone
Look in main() scope → found: x = 20 ✓ stop here

File-scope x = 10 is never reached in either case — it is shadowed.
🔧 Language Design Connection

C's design choice: Any block { } can introduce a new scope. The inner declaration does not replace the outer one — both exist simultaneously, but the inner one takes precedence within its block. This gives programmers flexibility but requires careful reading: a name can silently refer to a different variable than it appears to.

🔬 Trace the scope

In the code below, mark each use of x with which declaration it refers to:

int x = 1;            // Declaration A
void foo() {
    int x = 2;        // Declaration B
    {
        int x = 3;    // Declaration C
        printf("%d", x); // Use 1 — which declaration?
    }
    printf("%d", x);   // Use 2 — which declaration?
}
printf("%d", x);       // Use 3 — which declaration?

Use 1 → Declaration C (x = 3): Inside the innermost block, x refers to the nearest enclosing declaration — C.

Use 2 → Declaration B (x = 2): The inner block has closed, so Declaration C no longer exists. The nearest declaration is B.

Use 3 → Declaration A (x = 1): Outside foo(), B and C no longer exist. Only the file-scope A is visible.

This "nearest enclosing declaration" rule is the core of C's lexical scope. When multiple declarations share a name, the innermost one wins — the outer ones are shadowed (Section 6).

Section 4

Python: The LEGB Rule

Python has a formal, named scope rule: LEGB. When Python looks up a name, it searches through four layers in this order — stopping at the first match.

Python LEGB scope — search order (innermost → outermost)
L — Local

Names defined inside the current function. Python searches here first.

function parameters variables assigned in this function
E — Enclosing

Names in the local scope of any enclosing function (for nested functions). Python searches from the immediately enclosing function outward.

variables in outer() variables in outer-outer()
G — Global

Names defined at the module level — the top of the current .py file. Also where imported names land.

module-level variables functions defined at module level imported names
B — Built-in

Names Python always provides — built-in functions and constants. Python searches here last.

print len range type True / False / None int, str, list …

LEGB in action — a complete example

x = "global"         # G — global scope

def outer():
    x = "enclosing"  # E — enclosing scope (for inner)

    def inner():
        x = "local"  # L — local scope
        print(x)      # finds "local" immediately → prints "local"

    inner()
    print(x)          # outer's local x → prints "enclosing"

outer()
print(x)              # global x → prints "global"
print(len)            # B — found in built-ins → the built-in function len

The global and nonlocal keywords

By default, assignment inside a function creates a new local variable — it does not modify the enclosing or global variable of the same name. To modify a variable in an outer scope, you must explicitly declare your intent:

Python — global keyword
count = 0

def increment():
    global count    # "I mean the module-level count"
    count += 1      # modifies the global

increment()
print(count)  # 1
Python — nonlocal keyword
def outer():
    count = 0

    def inner():
        nonlocal count  # "I mean outer's count"
        count += 1

    inner()
    print(count)  # 1

outer()

Why require global and nonlocal? Python's design decision: assignment inside a function always creates a local binding by default. This prevents accidental modification of outer variables — a common source of bugs. The explicit global or nonlocal declaration makes the programmer state their intent clearly. C does not have this protection — assignment in a function always modifies whatever variable the name resolves to.

🔧 Language Design Connection

Python's designers chose the LEGB rule to support closures cleanly. Because the E (Enclosing) layer exists, an inner function can read variables from an outer function without any special syntax — the LEGB search finds them automatically. But to write to an outer variable, the programmer must be explicit (nonlocal). This design makes closures powerful while reducing accidental side effects. C made the opposite choice: no enclosing-function scope at all, keeping the model simpler but less expressive.

The UnboundLocalError trap

Python's "assignment creates a local" rule causes a surprising error that many Python programmers encounter:

x = 10

def broken():
    print(x)     # UnboundLocalError! Python sees x = x + 1 below
    x = x + 1   # this assignment makes x "local" for the whole function
                 # so reading x before the assignment fails

broken()

The trap: When Python processes a function, it scans the whole body for assignments. If it finds x = ... anywhere in the function, it treats x as local throughout the entire function — including lines before the assignment. Reading a local variable before it is assigned produces an UnboundLocalError. The fix is to add global x at the top of the function.

🤔 LEGB Trace

For each print statement, which LEGB layer does Python find the name in?

result = 100

def compute():
    multiplier = 3

    def apply(n):
        total = n * multiplier
        print(total)     # (1) total comes from which layer?
        print(multiplier) # (2) multiplier comes from which layer?
        print(result)    # (3) result comes from which layer?
        print(len)       # (4) len comes from which layer?

    apply(5)

compute()

(1) total → L (Local): total is assigned inside apply(), so it is local to apply(). Found immediately.

(2) multiplier → E (Enclosing): Not in apply()'s local scope. Python looks outward to compute(), which is the enclosing function — finds multiplier = 3 there.

(3) result → G (Global): Not local, not in any enclosing function. Found at module level where result = 100.

(4) len → B (Built-in): Not defined anywhere in the program — Python searches all the way to the built-in scope and finds the built-in function len.

Section 5

C#: Four Levels of Scope

C# has a richer scope hierarchy than C, reflecting its object-oriented design. For this course we use four useful levels to reason about C# names: block, method, class, and namespace. This is a teaching model — actual C# scope rules are more detailed, but these four levels cover the cases you will encounter most often.

C# scope hierarchy — outermost → innermost
Namespace scope

The broadest level. Classes, interfaces, enums declared inside a namespace block are visible throughout that namespace (and to other code that imports it). Equivalent to C's multi-file visibility.

namespace MyApp { ... }
Class / type scope

Fields and methods declared in a class are visible to all methods in that class (subject to access modifiers like private, public). C has no equivalent — it must simulate this with structs and conventions.

class fields class methods properties
Method scope

Parameters and local variables declared inside a method are visible from declaration to the end of the method. Equivalent to C's block scope at the function level.

method parameters local variables
Block scope

Variables declared inside a block (if, for, while, etc.) are visible only within that block. Same as C's innermost rule.

loop variables if-block variables

A complete C# scope example

namespace SchoolApp {           // namespace scope

    class Student {               // class scope
        private string name;    // visible to all methods in Student
        private int grade;

        public Student(string n, int g) {
            name = n;             // 'name' is the class field
            grade = g;
        }

        public void Report() {   // method scope
            string prefix = "Student:"; // method-local

            if (grade >= 90) {
                string msg = "Excellent"; // block scope — only here
                Console.WriteLine($"{prefix} {name} — {msg}");
            }
            // msg is NOT accessible here — block has ended
        }
    }
}

C# scope vs C scope vs Python scope

Scope levelCC#Python
Innermost blockBlock { }Block { }Not applicable — no { }
Function / methodFunction blockMethod scopeLocal scope (L in LEGB)
Enclosing functionNot supportedNot supportedEnclosing scope (E in LEGB)
Type / classNone (no classes)Class scopeClass body (limited)
File / moduleFile scopeNamespace scopeGlobal / module scope (G)
Language built-insNone (use #include)System namespaceBuilt-in scope (B in LEGB)

The design rationale behind C#'s extra levels: C# was designed for object-oriented software where code is organised into classes and namespaces. A field should be visible to all methods in its class; a class should be visible to all code in its namespace. C doesn't need these levels because it has no classes. Python has classes but handles their scope differently — a method doesn't automatically see the class's attributes without self.

🔧 Language Design Connection

Each additional scope level in C# reflects a structural unit in the language's design. Adding a class meant adding class scope. Adding namespaces meant adding namespace scope. The scope hierarchy is not arbitrary — it follows the language's organisational model. This illustrates a general principle: the scope rules of a language tend to mirror the abstraction mechanisms the language provides.

Section 6

Shadowing: When Inner Scope Hides Outer Scope

Shadowing occurs when a declaration in an inner scope uses the same name as a declaration in an outer scope. The inner declaration takes precedence within that scope — the outer one is invisible there, though it continues to exist.

Shadowing is a design decision, not just a technical mechanism. A language designer must decide: should inner scopes be allowed to reuse names from outer scopes, and if so, what are the rules?

LanguageIs shadowing allowed?Design choice
C Yes — any inner block variable can hide an outer variable Simplicity: no special rules, inner scope always wins
Python Yes — local/enclosing/global names can share a spelling Flexibility: LEGB search; global/nonlocal to override default
C# Partially — class fields can be shadowed; local-shadowing-local in the same method is restricted Safety: prevents a specific common mistake while preserving flexibility elsewhere
C — shadowing allowed, no warning
int x = 1;
void f() {
    int x = 2; // shadows global x
    printf("%d", x); // 2
}

No warning. The compiler silently uses the nearest x. Can cause subtle bugs if the shadowing is unintentional.

C# — some shadowing restricted
int x = 1;
if (true) {
    // int x = 2; — ERROR in C#
    // Cannot shadow a local variable
    // from the same method scope
}

C# disallows shadowing a local variable from the same method scope — a deliberate safety decision. Class fields CAN be shadowed by locals.

Python — shadowing allowed
x = "global"
def f():
    x = "local" # shadows global x
    print(x)   # "local"
print(x)       # "global"

Python allows shadowing. A local x does not modify the global x. The global remains intact after the function returns.

Shadowing a class field with a local variable (C#)

class Counter {
    private int count = 0;  // class field

    public void Broken(int count) {  // parameter shadows class field!
        count++;                      // increments the PARAMETER, not the field
        Console.WriteLine(count);     // prints parameter value
        Console.WriteLine(this.count); // use 'this' to reach the field
    }
}

The shadowing bug pattern: One of the most common bugs in C# (and Java) is accidentally naming a local variable or parameter the same as a class field. The local silently shadows the field. Using this.fieldName explicitly avoids this — but requires discipline. C# only blocks the narrower case of shadowing a local with another local in the same method.

When is shadowing intentional?

# Python — deliberate shadowing in comprehensions
items = [1, 2, 3, 4, 5]
result = [x * 2 for x in items]  # x is local to the comprehension
# In Python 3, x does NOT "leak" out of the comprehension
# This was a Python 2 bug — Python 3 fixed it by making comprehension
# variables have their own scope
🤔 Design Question

C# prevents shadowing a local variable with another local in the same method — but C and Python both allow it freely. Is shadowing a useful feature, a source of confusion, or both? What is C# trying to prevent, and what is it trading away?

What C# prevents: A programmer writes int x = 5; in a method, then later (in a nested block) writes int x = 10; — perhaps forgetting the first declaration. In C, the second x silently shadows the first, which can produce confusing bugs. C# makes this a compile error, forcing the programmer to use a different name.

What C# trades away: Sometimes using the same name in a nested block is intentional — loop counters, temporary variables. Restricting this requires programmers to invent new names.

The design lesson: There is no universally correct answer. C prioritises simplicity and flexibility. C# prioritises catching a specific class of bugs. Python prioritises making closures and nested functions natural. Each is a defensible choice, and each reflects the language's broader design philosophy.

Section 6b

Name Resolution: Connecting a Reference to Its Declaration

We have discussed scope rules for C, Python, and C#. Now let's make explicit the process those rules support.

Name resolution is the process of determining which declaration a particular use of a name refers to.

Every time code refers to a name, the language must resolve it. Scope rules define the algorithm. Symbol tables (Section 7) are the data structure that supports the algorithm.

The resolution algorithm — a procedure you can follow

  1. Find the use — identify the name being referenced.
  2. Identify the current scope — which function, block, or module is the reference in?
  3. Search the current scope — is there a declaration for that name here?
  4. If found — use that declaration. Stop.
  5. If not found — move outward to the enclosing scope, according to the language's rules.
  6. Continue outward — repeat until the name is found or there are no more enclosing scopes.
  7. If never found — the language determines what happens: usually an error (NameError in Python, "undeclared identifier" in C).

Tracing name resolution through nested Python scopes

Program with three levels of x
x = 100          # G — global

def outer():
    x = 50       # E — enclosing

    def inner():
        x = 10   # L — local
        print(x)  # ← resolve this

    inner()

outer()
Resolution trace for print(x)

x = 10 declared here → Found!
Stop. Use x = 10.

Output: 10
If inner's x = 10 is removed:

No x here.

x = 50 declared here → Found!

The procedure across all three languages

The same algorithm applies in all three languages — what differs is which scopes exist and in what order they are searched:

Notice the last row: C and C# report undeclared names at compile time — they refuse to run until all names are resolved. Python discovers undeclared names at runtime, when the relevant line executes. This is a direct consequence of static typing (C/C#) vs dynamic binding (Python) — a theme running through Chapters 3, 4, and 5.

Section 7

Symbol Tables: How Compilers Track Names

Section 6b described name resolution as an algorithm. Symbol tables are the data structure that makes that algorithm efficient. Every compiler or interpreter needs some mechanism to remember what names have been declared, where, and what their types and kinds are.

A symbol table is a data structure used by a compiler or interpreter to keep track of names — mapping each identifier to its kind, type, scope, and associated information.

A simple conceptual symbol table might look like this:

Scoped symbol tables — how nested scopes work

In practice, compilers maintain a stack of symbol tables — one per scope. When a new scope opens (a function is entered, a block starts), a new table is pushed onto the stack. When the scope closes, that table is popped.

Nested scopes → nested symbol tables

Because scope is hierarchical, a single flat table is not enough. Compilers maintain a stack of symbol tables — one per active scope. The structure reflects the source code nesting directly:

//   create and push a new table

// Declare a name:
//   record it in the top table

// Reference a name:
//   search top → ... → bottom
//   stop at first match

// Exit scope:
//   pop the top table
//   (names in it are gone)
🔧 Language Design Connection

The symbol table stack directly mirrors the scope hierarchy the language designer chose. A language with four scope levels (like C#) needs a four-layer stack. Python's LEGB rule maps directly: Built-in (always at the bottom), then Global, then Enclosing function tables, then Local at the top. The design decision about scope rules determines what the implementation must support.

Why symbol tables matter for programming language design

What symbol tables enableWhat this means for the language
Name resolution Determining which declaration a use of a name refers to — the core of scope rules
Type checking Once the compiler knows which variable is referenced, it can check whether operations on it are type-correct
Duplicate detection Reporting an error if the same name is declared twice in the same scope
Unused variable warnings Noticing that a name was added to the symbol table but never looked up
Optimisation Knowing the scope of a variable allows the compiler to allocate storage efficiently

Statically vs dynamically scoped languages: In a statically scoped language (C, C#, Python), the symbol table structure can be built at compile time — the compiler processes the source text and builds scope tables by reading the code. In a dynamically scoped language, name resolution depends on the runtime call stack — the compiler cannot build a definitive symbol table ahead of time. This is one reason static scoping enables better compile-time error detection.

Trace Exercise 2 — C scope

✏️ Manual Trace — C scope rules

For each numbered comment, identify which declaration the name resolves to (by line) and why:

#include <stdio.h>

int score = 100;      // Line 3: file scope

int bonus(int score) { // Line 5: parameter named "score"
    if (score > 50) {
        int extra = 10; // Line 7: block scope
        score += extra;  // (1) which "score"? which "extra"?
    }
    return score;        // (2) which "score"?
}

int main() {
    int result = bonus(score); // (3) which "score"?
    printf("%d\n", result); // (4) which "result"?
    return 0;
}

(1) score → the parameter (line 5), extra → the if-block local (line 7). Inside bonus(), the name score refers to the parameter, not the global (line 3). The parameter shadows the global. extra is local to the if block and is found immediately.

(2) score → the parameter (line 5). We are still inside bonus(). The if block has ended, so extra no longer exists. But score the parameter is still in scope for the entire function body.

(3) score → the global (line 3). Inside main(), there is no parameter named score and no local named score. The name resolves to the file-scope global score = 100.

(4) result → main()'s local. result is declared as a local variable in main() and that is the only result in any scope at this point.

Trace Exercise 3 — C# class scope

✏️ Manual Trace — C# four scope levels

For each numbered comment, identify the scope level the name comes from:

namespace Library {
    class Book {
        private string title = "Unknown"; // class field
        private int pageCount = 0;

        public void Update(string title, int pages) {
            this.title = title;        // (1) 'this.title' vs 'title'?
            pageCount = pages;         // (2) which 'pageCount'?

            if (pages > 500) {
                string note = "Long book"; // (3) scope of 'note'?
                Console.WriteLine(note);
            }
            // Console.WriteLine(note); // (4) would this work?

}

(1) this.title refers to the class field (class scope). The bare title on the right refers to the method parameter (method scope). The parameter shadows the class field, so this is needed to reach the field explicitly.

(2) pageCount refers to the class field. There is no local variable or parameter named pageCount, so the lookup reaches class scope and finds the field.

(3) note has block scope — it exists only inside the if block. It is not visible outside that block.

(4) No — this would be a compile-time error in C#. note is out of scope; the block that declared it has ended. C# (and C) are consistent here: block-scoped variables are inaccessible outside their block.

Section 9

Common Misconceptions About Scope

❌ Misconception 1

"Scope and lifetime are the same thing."

✓ Correction: Scope is WHERE in source code a name is accessible — a static, textual property. Lifetime is HOW LONG during execution the variable exists — a runtime property. A local variable's scope ends at the closing brace (textual), and its lifetime ends when the function returns (runtime). For most local variables they correspond, but they are different concepts and can come apart in edge cases (e.g. static local variables in C have function scope but program-long lifetime).

❌ Misconception 2

"Python's global keyword makes a variable visible everywhere."

✓ Correction: The global keyword inside a function does not create a new global variable or broadcast visibility. It tells Python: "when I write this name inside this function, resolve it to the existing module-level variable of that name, rather than creating a new local." It is a scope-resolution instruction, not a visibility declaration.

❌ Misconception 3

"Dynamic scoping and dynamic typing are the same concept."

✓ Correction: These are completely unrelated concepts. Dynamic typing is about when type checking occurs (at runtime rather than compile time) — covered in Chapter 3. Dynamic scoping is about how name resolution works (based on the call stack rather than the source text). Python has dynamic typing but static (lexical) scoping. The word "dynamic" appears in both but refers to different things.

❌ Misconception 4

"In Python, a function can always see and modify the global variables in its module."

✓ Correction: A function can always read a global variable (via LEGB, G layer). But to assign to a global variable from inside a function, you must declare it with global. Without that declaration, an assignment creates a new local variable with the same name — it does not modify the global. This distinction causes the UnboundLocalError trap described in Section 4.

❌ Misconception 5

"C# namespace scope is the same as Python's module scope."

✓ Correction: They play a similar organisational role but differ significantly. A Python module corresponds to a single .py file — it is the global scope for everything in that file. A C# namespace can span multiple files, and multiple namespaces can exist in one file. Python's module boundary is always a file; C#'s namespace is an explicit grouping construct that is independent of file structure.

❌ Misconception 6

"The LEGB rule means Python always checks all four layers for every name."

✓ Correction: Python stops at the first match. If a name is found in the L (Local) scope, Python uses it immediately and never checks E, G, or B. The rule defines the order of search, and the search stops early on success. This is why a local variable with the same name as a built-in (like naming a variable list) shadows the built-in within that function — the local is found first.

Before the Summary

Scope Rules Are Design Decisions

Before summarising, let's step back and look at the design questions every language designer must answer about scope and name resolution. These are not implementation details — they are fundamental choices that shape how programmers write and reason about code.

The questions

  • Should blocks create new scopes?
  • Should nested functions see their enclosing function's variables?
  • Should shadowing be allowed?
  • Should name lookup be based entirely on source structure?
  • How much should the language protect programmers from accidental name conflicts?
  • When should undeclared name errors be reported — at compile time or runtime?

The tradeoffs

  • Simplicity vs expressiveness
  • Flexibility vs safety
  • Readability vs implementation complexity
  • Early error detection vs runtime flexibility
  • Programmer control vs language-enforced constraints

There is no single "best" set of scope rules. C's simple block-scope model is powerful and efficient but requires programmer discipline. Python's LEGB rule makes closures natural but requires the global and nonlocal keywords to avoid surprises. C#'s four-level hierarchy mirrors its object-oriented structure but adds complexity. Each language made deliberate tradeoffs.
