What Really Happens When We Create a Variable?

Where we left off: Chapter 2 asked how does a language recognise code? — tokens, syntax, grammar. Now we ask the next question: what does a language mean by a variable, and how does that variable behave? Languages don't just differ in how code looks. They differ in what program constructs mean.

Start with one familiar line:

Python
age = 25

You've written lines like this hundreds of times. But let's slow down and ask five questions about it:

① What is age? Just a label? A memory location? Something else?
② Where is 25? In what sense does age "contain" it?
③ Does age have a type? Who decided that, and when?
④ When does Python decide what age refers to?
⑤ How long does age exist?
🤔 Think First

Before reading on: write down your best answers to those five questions. Don't worry about being technically precise — just describe what you think is happening.

① What is age? It's a name — an identifier the programmer chose. In Python, that name is associated (or "bound") with an object. It is not a fixed container the way a labelled box in a warehouse is fixed — the name can be redirected to a different object later.

② Where is 25? Python creates an object representing the integer 25. The name age refers to (or points at) that object. The object lives somewhere in memory — the programmer doesn't manage exactly where.

③ Does age have a type? Yes — but it's the object that has a type (integer), not the name. The name age itself has no type; it can be redirected to an object of any type.

④ When does Python decide? At runtime — when that line actually executes. Python does not analyse types before running your code.

⑤ How long does age exist? For as long as the scope it lives in is active. If this is at the top level of a script, until the script ends. If inside a function, until the function returns.

These five questions — name, value, type, when associations are established, and how long they last — are the questions every programming language must answer about every variable. The answers C, C#, and Python give are genuinely different. That's what this chapter is about.

The central idea of this chapter: A variable is more than just a box containing a value. A programming language must decide what the variable is associated with, when those associations are established, and how long they last.

Section 1

Questions a Language Must Answer About Variables

Rather than listing attributes as if they were universal rules, let's ask the questions that every programming language designer must answer. C, C#, and Python give different answers — and those differences are the point of this chapter.

Question 1 — What is its name?

How does the programmer refer to it? In age = 25, the name is age. Names must be valid identifiers (recall Chapter 2: identifiers are a token type). The name is the human-readable handle — but it is not the same as the value, the type, or the storage location. It is just a label.

This distinction between a name and what it refers to becomes especially important in Python, where a name can be redirected to refer to a completely different object.

Question 2 — What kind of data can it represent?

Is its type declared by the programmer, inferred by the compiler, or determined dynamically at runtime? Types matter because they determine which operations are valid — and who is responsible for catching type mistakes.

C — programmer declares
int age = 25;
float gpa = 3.8;
// Type is in the source code
C# — explicit or inferred
int age = 25;
var gpa = 3.8;
// var: compiler infers type
Python — no declaration
age = 25
gpa = 3.8
# No type token written —
# but objects still have types!

Critical: The absence of a type declaration in Python does not mean the value has no type. Every Python object has a type — type(25) returns <class 'int'>. What Python doesn't have is a place in the syntax where you write it. The design question is: who is responsible for tracking type information, and when?

Question 3 — What value does it currently hold?

In age = 25, the current value is 25. This can change — age = 26 updates it. The value is distinct from the name: the name age is a stable label; 25 is what it currently represents.

Question 4 — How is that value accessed or stored?

When code reads age, the language runtime must somehow locate the data. The details of that mechanism differ between languages: C gives you more direct access to memory locations; C# and Python manage this automatically. You don't need to know the hardware details — just that it exists, and that different languages give you different levels of control over it.

💡 Conceptual model

Think of it like a contact name in a phone book. The name "Dee" (the variable name) lets you look up a phone number (the actual data). C lets you know which "page" in the book and manipulate it directly. Python and C# manage the lookup for you. The design question is: how much control should the programmer have?

Question 5 — How long does the name or variable exist?

Lifetime is the period during program execution when the variable exists and can be used. It is about time, not place. A variable is created at some point, and at some later point it ceases to exist.

Scope (Chapter 4) asks where in source code a name is visible. Lifetime asks how long during execution the variable or object exists. These are related but different — keep them separate in your mind from the start.

The design connection: These five questions don't have universally agreed answers. C, C#, and Python each make different choices. Those choices determine how flexible the language is, when errors are caught, how much the programmer must write, and who is responsible for managing resources. That's what we're here to understand.

The five questions at a glance

A variable involves...
① Name ← how the programmer refers to it
② Type ← what kind of data, and who/when determines this
③ Value ← what it currently represents
④ Storage ← how the runtime finds the data
⑤ Lifetime ← how long it exists during execution
🔬 Classify

For int score = 95; in C, identify the name, type, and value. Then: which of these five questions does the programmer answer explicitly by writing this line?

Name: score · Type: int · Value: 95

The programmer explicitly answers questions ①, ②, and ③ in this single line. Question ④ (storage) is handled by the compiler automatically. Question ⑤ (lifetime) is determined by where this declaration appears — inside a function means it lives for that function call.

In Python's score = 95, the programmer explicitly answers only ① (name) and ③ (value). Question ② (type) is answered by Python at runtime based on the object. Questions ④ and ⑤ are managed by the runtime. That's two fewer things to write — and a different set of tradeoffs.

Section 1b

Declaration vs. Assignment: What Does Each Language Require?

Before going deeper into binding, let's clarify two programming concepts that look similar but are conceptually separate — and that different languages handle very differently.

Declaration

Telling the language that a variable exists, and often what type it holds. In C, you must declare before you use.

Assignment

Giving a variable its value. This can be done at declaration time, or separately later.

In C — declaration and assignment are separable

Separate declaration and assignment
int age;       // declaration: name + type
age = 25;      // assignment: give it a value
Combined (more common)
int age = 25;  // declaration + initialization

In C, the type is always part of the declaration. The programmer must write it. There is no way to create a variable without specifying its type.

In C# — same structure, with optional inference

Explicit type
int age = 25;
Type inference
var age = 25;
// compiler infers: int
Separate (also valid)
int age;
age = 25;

var does NOT mean "dynamically typed." The compiler infers that age is an int at compile time — from the value 25. After that, the type is fixed. You still cannot assign a string to it later.

In Python — no declaration syntax

Assignment creates the binding
age = 25
# No separate declaration step
Name can later refer to a different type
age = 25
age = "hello"
# Both are valid in Python

Python does not have a declaration step separate from assignment. When you write age = 25, that assignment is what creates the name. There is no type information to provide — the name is simply bound to an object, and the object carries its own type.

Why didn't all three languages choose the same approach?

C and C# require declarations because…

  • Explicit type information enables the compiler to check for type errors before running
  • More constraints mean certain bugs are impossible by design
  • Useful in large codebases where clarity matters

Python skips declarations because…

  • Less to write — faster to develop and prototype
  • More flexibility — the same name can refer to different things
  • Type information is handled at runtime rather than write-time

Neither approach is universally better. They reflect different priorities: C/C# prioritise compile-time certainty and explicitness. Python prioritises conciseness and runtime flexibility. Both are valid design choices with different tradeoffs.

Section 2 — The Most Important Concept

Binding: When Names Get Connected to Things

Now that we understand a variable's attributes separately, we can introduce the concept that ties them together.

Binding is the process of establishing a connection between a program entity and some property, resource, or meaning associated with it.

That definition sounds abstract, so let's make it concrete. A program has many kinds of entities that need to be connected to things:

EntityConnected toExample
A nameA variable or storage locationage refers to a particular slot in memory
A variableA typeage is declared as int in C
A variableA valueage currently holds 25
A nameAn object (Python)age refers to the integer object 25
An operator symbolIts meaning+ means integer addition when used with integers — a binding the language designer decided

The key insight: different programming languages establish these connections at different times — some before you run the program, some as it runs. That "when" has big consequences for programmers.

When a language processes int age = 25;, it creates several bindings at once:

What is connectedExample connectionWhat this binding enables
Name ↔ Typeage is bound to intThe compiler can check that operations on age are valid for integers
Name ↔ Valueage is bound to 25Reading age returns 25
Name ↔ Storageage is bound to a locationThe runtime knows where to read and write the value

Why Python's rebinding is possible

Now consider this Python code:

age = 25
age = "twenty-five"

In C, the equivalent is impossible:

int age = 25;
age = "twenty-five";  /* compile error: incompatible types */

Why can Python do something C cannot? The difference comes from what the name is bound to:

In C

The name age is bound to a specific type (int) at declaration time. That binding is permanent for the lifetime of the variable. Assigning a string to an int variable violates the type binding — the compiler rejects it.

In Python

The name age is not bound to a type. It is bound to an object. The object has a type. When you write age = "twenty-five", you are not changing the type of age — you are creating a new string object and rebinding the name age to point at it instead.

Precise language matters here. Do not say "Python variables change type." The more accurate statement is: in Python, a name can be rebound to an object of a different type. The original object does not change its type. The name simply points to a different object.

Visualising binding in Python

After age = 25:
age ─────→ 25 int object
After age = "twenty-five":
age ─────→ "twenty-five" str object
The integer object 25 still exists in memory until Python's garbage collector reclaims it. The name age simply no longer refers to it.
🤔 Predict the Output

What does this Python program print?

x = 10
x = "hello"
print(x)

Output: hello

First, x is bound to the integer object 10. Then x is rebound to the string object "hello". When print(x) runs, x refers to the string, so "hello" is printed.

Notice: the integer object 10 is not destroyed immediately — Python's garbage collector handles memory. But the name x no longer refers to it. For all practical purposes, once nothing refers to an object, it can be reclaimed.

Section 3

Binding Time: When Are Connections Established?

We now know that binding means establishing a connection. But connections don't all have to be established at the same time. Binding time answers a simple question:

When is a relationship determined?

Some relationships are fixed early — even before the program runs. Others are established only when the code actually executes. A language can decide different relationships at different times.

Types of binding time

When binding occursCalledExample
When the language is designedLanguage-design timeThe meaning of + for integers is fixed by the language itself
When the program is compiledCompile timeIn C, int age binds the name to the type int at compile time
When the program starts runningLoad time / link timeGlobal variables in C get storage allocated when the program loads
When a specific line executesRuntimeIn Python, x = 10 creates the binding when that line runs

Static binding — connections established early

A binding is static when it is determined before execution — most commonly at compile time. The connection is fixed and does not change while the program runs.

C — static type binding
int age = 25;
// The binding of "age" to type "int" is established at compile time.
// No matter what happens at runtime, age is always an int.
C# — type binding at compile time (even with var)
var age = 25;
// The compiler infers: age is an int.
// That binding is fixed at compile time — age cannot be rebound to a string later.

Dynamic binding — connections established at runtime

A binding is dynamic when it is determined during execution. The connection can potentially be different each time the code runs, or change as the program runs.

Python — runtime binding
x = 10
x = "hello"
# The binding of "x" to an object is established at runtime,
# when each assignment statement executes.

⚠ Don't confuse these — students mix them up constantly:

ConceptMain questionExample
Binding time When is any particular relationship established? C binds a name to its type at compile time; Python binds a name to an object at runtime
Static typing When are type rules checked? C and C# check types at compile time — before the program runs
Dynamic typing Are type checks deferred to runtime? Python checks types at runtime — when the code actually executes

Typing (static vs dynamic) is a specific dimension of binding time — it is about when type relationships are checked. But binding time is a broader concept: it applies to names, storage, values, and other relationships too. Don't use one term as a synonym for the other.

🤔 Classify the Binding

For each of the following, is the binding of the name to its type static or dynamic?

A: int count = 0; (C)
B: var count = 0; (C#)
C: count = 0 (Python)

A — Static. The name count is explicitly bound to type int at compile time. The compiler enforces this binding throughout the program.

B — Static. Even though you used var, the compiler infers that count is an int from the value 0. That type binding is established at compile time, not at runtime. var is shorthand for the compiler, not a runtime decision.

C — Dynamic. The binding of the name count to the integer object 0 is established when that line executes at runtime. There is no compile-time determination of type.

Section 4

Variable Lifetime: How Long Does It Exist?

The lifetime of a variable is the period during program execution when the variable exists and can be used. Variables are created, used, and eventually cease to exist.

Lifetime with a simple function

The clearest way to see lifetime is with a local variable inside a function:

C
void greet() {
    int age = 25;
    printf("%d", age);
} // age ends here
C#
void Greet() {
    int age = 25;
    Console.WriteLine(age);
} // age ends here
Python
def greet():
    age = 25
    print(age)
# age ends when greet() returns

The lifetime timeline

Function is called
Execution enters greet()
Variable is created
age comes into existence — storage is allocated, the binding is established
Variable is used
age is read, printed, or modified
Function returns — lifetime ends
age ceases to exist. Any attempt to access it after this point is an error.

Scope vs Lifetime — a critical distinction

Scope

Where in the source code a name can be accessed. Scope is a static, textual property — you can determine it by reading the code, before running it.

Covered fully in Chapter 4.

Lifetime

How long during execution the variable exists. Lifetime is a dynamic, runtime property — it depends on what actually happens when the program runs.

Covered in this chapter.

They often correspond — a local variable is usually both inaccessible outside its function (scope) and doesn't exist outside its function call (lifetime). But they are conceptually separate, and in some cases they come apart. For now, keep the definitions distinct.

Global variables — a different lifetime

C — global variable
int globalCount = 0;
// Lives for the entire
// program execution

void increment() {
    globalCount++;
}
Python — module-level name
count = 0
# Lives while the module
# is loaded

def increment():
    global count
    count += 1

Global variables have a lifetime that spans the entire program run — they are created when the program starts and cease to exist when it ends. Local variables have a shorter lifetime tied to a specific function call.

Important: A name's lifetime ≠ an object's lifetime

In Python especially, there is a distinction that surprises many programmers: the name that refers to an object can stop being accessible while the object itself continues to exist.

def create_person():
    person = {"name": "Dee"}
    return person

p = create_person()

Inside create_person(), the name person refers to the dictionary object. When the function finishes, the local name person is no longer accessible — it no longer exists as a local name.

But the dictionary object continues to exist — because p in the outer scope now refers to it. Python's runtime keeps the object alive as long as something still refers to it.

The key lesson: In Python, the lifetime of a name/binding and the lifetime of the object it refers to are not necessarily the same. A name can disappear while the object lives on — as long as another name still refers to it.

💡 Analogy

Imagine a document shared between coworkers. If one colleague deletes their shortcut to it, the document is not gone — others still have access. The object (document) outlives the reference (shortcut) that one person held. Python's memory model works similarly: objects persist as long as at least one reference to them exists.

Section 5

Stack & Heap: Where Do Variables Live?

Conceptual model alert: This section presents a simplified but useful model of how memory works. The actual behaviour of any particular language or compiler may be more complex. The goal here is to understand enough to reason about variable lifetime and language design — not to learn systems programming.

When a program runs, its data has to be stored somewhere in memory. Two common conceptual regions are the stack and the heap. Different languages give programmers different levels of control over which is used.

The Stack

A region typically associated with function calls. When a function is called, space is allocated for its local data. When the function returns, that space is freed. The lifetime of stack-allocated data is tied to the function call.

Stack allocation is fast and automatic — no programmer action needed. The tradeoff: the data cannot outlive the function call that created it.

The Heap

A region used for data that needs to outlive a specific function call, or whose size isn't known at compile time. Heap memory can be explicitly requested (in C, via malloc) or allocated automatically by a runtime (Python, C#).

Heap allocation is more flexible — data can exist as long as needed. The tradeoff: someone must manage the memory, either the programmer (C) or the language runtime (C#, Python).

How our three languages approach memory management

Rather than saying "which variables go where," the more useful question is: who manages memory, and how much control does the programmer have?

C

Programmers have significant control over memory. Local data within a function is handled automatically. But to create data that outlives a function call, the programmer must explicitly request memory (malloc) and explicitly release it (free). Missing a free causes a memory leak; accessing memory after freeing it causes a crash.

C#

The managed runtime handles most memory automatically. Local data in functions is handled for you. Objects are managed by a garbage collector, which reclaims memory when it is no longer needed. You don't call free. The tradeoff is less direct control and some runtime overhead from the GC.

Python

The runtime manages objects and memory automatically. Programmers never explicitly allocate or free memory. Python uses reference counting and a garbage collector to clean up objects when they are no longer reachable. This simplifies code considerably at the cost of some runtime overhead.

Looking ahead: Memory management — garbage collection, reference counting, and how languages reclaim memory — is an important topic in its own right. We will return to it in later chapters. For now, the key design question is: how much control should the programmer have, and what are the tradeoffs?

❌ Oversimplification to avoid

"Value types always go on the stack; reference types always go on the heap."

✓ Better: Stack and heap are useful ways to think about how runtimes may organise memory, but they are implementation concepts — not universal rules about categories of variables. The same language may store the same kind of data differently in different contexts. What matters for this course is the design question: who manages memory, and what are the tradeoffs for programmers?

❌ Another common mistake

"Garbage collection means memory is freed immediately when a variable goes out of scope."

✓ Better: Garbage collection means the runtime will eventually reclaim memory that is no longer reachable — timing is not guaranteed to be immediate. In Python, reference counting frees many objects quickly, but objects in reference cycles require a separate collector. The object may also persist if any reference to it still exists, even after the local name that created it has gone away (as in the create_person() example in Section 4).

Section 6

C: Explicit Control Over Every Attribute

C gives the programmer more direct control over variables than almost any other mainstream language. This comes with both power and responsibility.

C — basic variable declarations
int   age   = 25;    // integer, 4 bytes
float gpa   = 3.8;   // floating point, 4 bytes
char  grade = 'A';   // single character, 1 byte

In every C declaration, the programmer must state the type explicitly. The type is bound at compile time and cannot change. Assignment must be compatible with the declared type — the compiler enforces this.

Local vs dynamic memory in C

Local variable — stack lifetime
void process() {
    int score = 95;
    // score exists until
    // process() returns
}

The lifetime of score is tied to the function call. Created when process() is called, gone when it returns.

Dynamic memory — heap lifetime
int *nums =
  malloc(5 * sizeof(int));
// nums points to heap memory
// Must call free(nums) later
free(nums);

The programmer controls when heap memory is created (malloc) and destroyed (free). Miss the free → memory leak. Access after free → crash.

The concept of uninitialized variables

One specific consequence of C's explicit control: C allows you to declare a variable without initializing it. This is legal syntax — but reading an uninitialized variable produces undefined behavior.

C — uninitialized variable
int score;
// score exists — but contains
// whatever happened to be in
// that memory slot. Could be 0,
// could be 42839, could be
// anything.
printf("%d
", score); // ⚠
C# — prevents this
int score;
// C# compiler gives an error:
// "Use of unassigned local
// variable 'score'"
// Prevents this class of bug
// at compile time.

Design lesson: C's choice to allow uninitialized variables gives the programmer flexibility (sometimes useful for performance). C# chose to make this a compile-time error — trading that flexibility for safety. Python cannot have this problem at all, because a name only exists after it has been assigned. This is another concrete example of how a design decision about variables shapes the bugs that are possible in a language.

The language design question

C's approach raises a fundamental design question: What does giving the programmer this level of control make possible — and what risks does it introduce?

✓ What it makes possible

Precise control over when memory is used and freed. Predictable performance — no garbage collector pausing at unexpected moments. Ability to write operating systems, device drivers, and real-time systems where exact timing matters.

✗ What risks it introduces

Memory leaks (forgot to free). Use-after-free (accessed freed memory). Buffer overflows (wrote past the end of an array). Uninitialized variables. These are among the most common and most serious bugs in C programs — and many are impossible in Python and C# because those languages were designed to prevent them.

Section 7

C#: Static Types with Convenience and Safety

C# keeps static typing (types determined at compile time) but adds two important features: type inference via var, and automatic memory management via garbage collection.

Explicit type vs type inference

Explicit type declaration
int age = 25;
string name = "Alice";
// Type written by programmer
Type inference with var
var age = 25;
var name = "Alice";
// Compiler infers: int, string

var in C# does NOT mean "dynamically typed." When you write var age = 25;, the compiler infers that age is an int at compile time. That type binding is just as static as if you had written int age = 25;. The difference is only in what you type — the compiler does the work of figuring out the type.

The proof: var is statically typed

var age = 25;
age = 30;          // ✓ valid — both ints

// age = "hello";  // ✗ compile-time error
// Cannot implicitly convert type 'string' to 'int'

If var meant dynamic typing, the second assignment would work. It doesn't. The name age is permanently bound to the type int at compile time — the compiler just figured out that type for you.

C# vs Python: the crucial comparison

C# — type binding is static
var x = 10;
// x is now int, forever.
// x = "hello"; → error
Python — name can be rebound
x = 10
x = "hello"  # perfectly valid
print(x)    # prints: hello

Both look similar on the first line. But in C#, the compiler infers an int type for x and that binding cannot be changed. In Python, x is not bound to any type — it refers to an object, and can be rebound to any object.

Section 8 — Key Conceptual Section

Python's Variable Model: Names and Objects

Python's approach to variables is fundamentally different from C and C#. Understanding the difference is one of the most important conceptual takeaways of this chapter.

The classic mental model (for C and C#)

In C and C#, it's reasonable to think of a variable as a typed box:

C mental model:
┌──────────────────────┐
│ age [type: int] │ ← 25
└──────────────────────┘
The box is typed. You can change the number inside, but you cannot put a string in an int box.

Python's actual model: names refer to objects

In Python, the model is different. Names are not typed boxes — they are labels that can be attached to any object:

After age = 25:
age ────→ 25 [object, type: int]

After age = "hello":
age ────→ "hello" [object, type: str]

The name age is just a label. Objects have types. Labels can point to any object. When you "reassign" age, you redirect the label — the old object is unchanged.

Names can point to the same object

x = 10
y = x
# Now both x and y refer to the same integer object 10
# x is y → True (they point to the same object)

x = 20
# Now x refers to 20. y still refers to 10.
# Rebinding x does NOT change y.
🤔 Predict the Output

What does this print? Think through the name-to-object binding carefully.

x = 10
y = x
x = 20
print(y)

Output: 10

Step 1: x is bound to the integer object 10.

Step 2: y is bound to the same object that x refers to — also 10.

Step 3: x is rebound to the integer object 20. This does NOT affect y — y still refers to 10.

Step 4: print(y) prints 10.

If you expected 20, you were using the "box" mental model. In the box model, y = x would mean "make y share x's box," so changing x would change y too. But Python doesn't work that way — assignment rebinds names to objects, it doesn't link boxes together.

Why objects have types — names do not

x = 42
print(type(x))       # <class 'int'>
x = "hello"
print(type(x))       # <class 'str'>

When you call type(x), Python is not reporting the type of the name x. It is reporting the type of the object that x currently refers to. The name x has no type — it is just a label.

When two names refer to the same object — aliasing

Because names in Python are references to objects, multiple names can refer to the same object. This is called aliasing, and it has consequences that the "box" mental model doesn't prepare you for.

a = [1, 2, 3]
b = a            # b refers to the SAME list object as a

b.append(4)      # modifying the object through b...

print(a)         # [1, 2, 3, 4] — visible through a too!

When you write b = a, you are not copying the list. You are creating a second name (b) that refers to the same list object. When b.append(4) modifies that object, the change is visible through a as well — because they both refer to the same thing.

Aliasing — both names share the object
a = [1, 2, 3]
b = a
b.append(4)
print(a)  # [1, 2, 3, 4]
# Modifying through b
# affects a too
Rebinding — not the same as aliasing
a = 5
b = a
a = 10
print(b)  # 5
# Rebinding a to 10 does
# NOT change b

Why these behave differently: In the second example, a = 10 creates a new binding — it redirects a to point at a different object. It doesn't modify the object 5 itself (integers in Python are immutable anyway). b still refers to 5. But in the first example, b.append(4) mutates the list object that both names refer to — so both see the change.

🤔 Predict

What does this print, and why?

a = [1, 2, 3]
b = a
b = [4, 5, 6]
print(a)

Output: [1, 2, 3]

Here, b = [4, 5, 6] is a rebinding — it makes b point to a brand new list. It does not modify the original list object. a still refers to [1, 2, 3]. Compare with the earlier example where b.append(4) mutated the shared object — that is a very different operation.

The key insight: Python is strongly typed — every object has a definite type and Python enforces type rules (you cannot add a string to an integer). But Python uses dynamic binding — names are not bound to types, only to objects, and names can be rebound at any time. These two facts together explain why Python behaves the way it does.

🔎 Design Analysis Activity

Work through these questions about the comparison above. Expand each to check your thinking.

Q1 — Why can Python rebind a name to a different type when C and C# cannot?
In Python, names are not bound to types — they are bound to objects, and objects have types. Because the name itself carries no type information, it can be redirected to an object of any type. In C and C#, the variable declaration binds the name to a specific type at compile time, and that binding cannot be changed.
Q2 — C# uses var and Python uses no declaration. Are these the same thing?
No. var in C# means "infer the type at compile time and then treat it as statically typed." The compiler figures out the type from the right-hand side. Python's lack of declaration means "bind the name to an object at runtime; no type is associated with the name." The result looks similar in source code but the behavior is fundamentally different — C#'s var is still statically typed, Python's is dynamically typed.
Q3 — Both C and C# prevent rebinding to a different type. What design goal does this serve?
Static type binding enables the compiler to catch type errors before the program runs. If you accidentally assign a string to an integer variable, you get an error immediately at compile time — not after the program has been running for hours and suddenly crashes. This is especially valuable in large codebases where a type mistake might only be triggered in a rare code path.
Section 10

Design Tradeoffs: Why No Single "Best" Variable Model

Think like a language designer. Each approach to variables reflects deliberate choices about what to prioritise. Here is the honest case for each.

C — Explicit, Static, Programmer-Controlled

✓ Advantages

  • Maximum control over memory layout and lifetime
  • Predictable performance — no GC pauses
  • Types checked at compile time — many errors caught early
  • Suitable for operating systems, embedded systems, real-time software

✗ Costs

  • Programmer responsible for memory management — bugs are serious
  • More verbose — every type must be stated
  • No safety net for memory errors (leaks, use-after-free)
  • Longer development time for many tasks
C# — Static Types + Safety + Inference

✓ Advantages

  • Static type checking catches errors at compile time
  • Type inference reduces verbosity without losing safety
  • Automatic memory management (GC) prevents most memory bugs
  • Good balance for large teams building complex software

✗ Costs

  • GC overhead — runtime performance slightly less predictable
  • More complex language with many features to learn
  • Less control over exactly when memory is freed
Python — Dynamic Binding + Flexibility

✓ Advantages

  • Concise — no type declarations to write
  • Flexible — names can refer to any object
  • Rapid prototyping and scripting
  • Automatic memory management

✗ Costs

  • Type errors only discovered at runtime
  • No compile-time type enforcement
  • Performance overhead from dynamic binding and GC
  • Harder to reason about types in large codebases

Before the Quiz

Common Misconceptions

❌ Misconception 1

"Python variables have no type."

✓ Correction: Python values (objects) always have a type. type(25) is int. type("hello") is str. What Python doesn't have is a type declaration attached to the name. The name has no type — the object does. Python is strongly typed but dynamically typed.

❌ Misconception 2

"var in C# means dynamically typed — just like Python."

✓ Correction: var is type inference, not dynamic typing. The C# compiler determines the type at compile time from the right-hand side of the assignment. The variable is then statically typed for its entire lifetime. var x = 25; means "compiler, figure out the type" — not "this variable can hold any type at runtime."

❌ Misconception 3

"A variable is just a box containing a value."

✓ Correction: A variable has multiple attributes: name, type, value, location, and lifetime. In Python especially, the "box" model is misleading — a name is a reference to an object, not a container. When you write y = x, you're pointing both names at the same object, not copying the box.

❌ Misconception 4

"Scope and lifetime are the same thing."

✓ Correction: Scope is where in the source code a name is visible. Lifetime is how long during execution the variable exists. They often correspond for local variables, but they are separate concepts. A variable can have ended its lifetime but still technically be "in scope" in edge cases, and vice versa in some language designs.

❌ Misconception 5

"Dynamic typing means Python has weak typing."

✓ Correction: Dynamic typing means types are checked at runtime (not compile time). Weak typing means the language silently converts between incompatible types. Python is dynamically typed but strongly typed — it will raise a TypeError if you try to add a string to an integer. JavaScript is weakly typed — it silently produces "hello5" from "hello" + 5.

❌ Misconception 6

"When a Python name is rebound to a different type, the object itself changed type."

✓ Correction: Objects in Python do not change type. When you write x = "hello" after x = 25, the integer object 25 is unchanged — it is still an int. The name x was rebound to point at a different object (the string). The original object still exists until garbage-collected.

❌ Misconception 7

"All local variables are always physically stored on the stack."

✓ Correction: Stack and heap are useful conceptual models for reasoning about memory, but they are not universal implementation rules. In Python, all objects are heap-allocated. Compilers optimise variable storage in ways that may not match a simple stack model. Always treat stack/heap as a thinking tool, not a strict guarantee about where any particular variable lives.

❌ Misconception 8

"b = a in Python copies the value of a into b."

✓ Correction: b = a makes b refer to the same object that a refers to. If that object is mutable (like a list), then changes made through either name are visible to the other — because they share one object. For immutable objects (like integers or strings), this distinction rarely matters in practice, but the model is still: two labels, one object — not a copy.
