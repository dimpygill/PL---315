Programming Language Design

Boxing and Unboxing in C, C#, and Python

One task, three approaches: store the integer 25, retrieve it, and add 5. Then explain what each language actually does.

Key distinction · C solution · C# solution · Python solution · Design comparison

1. Understand the distinction first

C: manual wrapper

Define a struct and copy an integer into its field. This is a custom representation, not a built-in boxing conversion.

C#: boxing / unboxing

Convert an int value to object, then explicitly recover the int value. These are language-defined operations.

Python: object references

Put a reference to an existing integer object into a list and retrieve it. No separate C#-style conversion is needed.

Important vocabulary: a value type holds a value as its data; a reference identifies an object. A wrapper holds another value. A cast requests an explicit conversion. Binding associates a name with an object; rebinding changes that association.

These examples deliberately produce the same output. Equal output does not imply equal storage behavior, equal safety guarantees, or equal execution cost.

2. C — create a manual wrapper

Complete program: main.c

Code

#include <stdio.h>

/* A programmer-defined wrapper containing one integer. */
typedef struct {
    int value;
} IntBox;

int main(void)
{
    int original = 25;

    /* Copy the integer into the wrapper's field. */
    IntBox container = { original };

    /* Read the field and copy its value into another int. */
    int retrieved = container.value;
    int result = retrieved + 5;

    printf("Original: %d\n", original);
    printf("Retrieved: %d\n", retrieved);
    printf("Result: %d\n", result);

    /* Changing the original does not change the earlier copy. */
    original = 100;
    printf("Original after change: %d\n", original);
    printf("Stored after change: %d\n", container.value);

    return 0;
}

StatementWhat it does
typedef struct { int value; } IntBox;Creates a type named IntBox with an int field named value. It can hold an integer; it is not a universal container for arbitrary types.

original = 100;Changes original only; container.value remains 25.

Storage and limitations

  • No dynamic allocation: the wrapper is an ordinary local object with automatic storage duration. This program does not call malloc or free.
  • No object header or runtime type tag: this struct contains only its declared field, plus any padding required by the implementation. It does not automatically carry C#-style boxed-object metadata.
  • No guaranteed exact byte count: int size and struct layout depend on the implementation. A one-field wrapper may occupy the same size as its field; do not assume it necessarily adds bytes.
  • Limited flexibility: supporting several kinds of values would require additional design, such as a tagged union with explicit checks.

Type safety in this example: the compiler knows that container.value is an int. C is statically typed, but its lower-level features, including unchecked pointer misuse, can bypass protections. That broader risk is not an error in this particular program.

Why a pointer cast alone is not boxing

Additional snippet

int value = 25;
void *pointer = &value;       // Store the address of the existing int.
int retrieved = *(int *)pointer; // Valid while value is alive and type is correct.

This pointer example creates no boxed copy and records no automatic runtime type information. The pointer still refers to the original int. Dereferencing it through an incompatible type or after its lifetime ends can cause undefined behavior. A cast does not make an incorrect pointer safe.

3. C# — built-in boxing and unboxing

Complete program: Program.cs

Code

using System;

// Top-level statements: the compiler supplies the entry point.
int original = 25;

// Boxing: object receives a reference to a boxed copy of the int.
object container = original;

// Unboxing: the runtime checks for a boxed int, then its value is copied.
int retrieved = (int)container;
int result = retrieved + 5;

Console.WriteLine($"Original: {original}");
Console.WriteLine($"Retrieved: {retrieved}");
Console.WriteLine($"Result: {result}");

// The boxed copy keeps the value stored earlier.
original = 100;
Console.WriteLine($"Original after change: {original}");
Console.WriteLine($"Stored after change: {(int)container}");

Expected output

Output

Original: 25
Retrieved: 25
Result: 30
Original after change: 100
Stored after change: 25
StepExplanation
int original = 25;int is a value type. The variable starts with the value 25.
object container = original;Boxes a copy of the integer. The variable container holds a reference to the boxed value; its declared type is object.
int retrieved = (int)container;Checks that container refers to a boxed int and copies its value into retrieved. The explicit cast requests unboxing.
original = 100;Changes the original variable. The earlier boxed copy still holds 25.

What overhead does this introduce?

  • Boxing: an object allocation and a value copy, with object metadata and alignment contributing to storage cost.
  • Unboxing here: a runtime type check and a copy into an int variable. It does not require creating another box.
  • Lifetime management: boxed objects can contribute to garbage-collection work when they become unreachable.

The semantic model uses a boxed object on the managed heap. Exact physical storage and measured costs depend on the runtime and optimization. Avoid the claim that all value types always live on the stack.

Incorrect unboxing: the exact value type matters

Run this as a separate Program.cs example:

Code

using System;

object container = 25; // The literal 25 has type int and is boxed as int.

try
{
    long wrong = (long)container; // Attempts to unbox as long, not int.
    Console.WriteLine(wrong);
}
catch (InvalidCastException)
{
    Console.WriteLine("Cannot unbox a boxed int directly as long.");
}

long correct = (int)container; // Unbox as int, then widen int to long.
Console.WriteLine($"Correct value: {correct}");

Expected output

Cannot unbox a boxed int directly as long.
Correct value: 25

Why it fails: numeric conversion and unboxing are different operations. Although an int value can widen to long, a boxed int is not a boxed long. Unbox to int first, then convert. Likewise, a string containing "25" requires parsing; casting an object that contains that string to int does not parse it.

Avoid unnecessary boxing with List<int>

Independent example

using System;
using System.Collections.Generic;

List<object> general = new List<object>();
general.Add(25);                    // int is boxed when added.
int a = (int)general[0];            // Explicit unboxing.

List<int> numbers = new List<int>();
numbers.Add(25);                    // No per-element boxing here.
int b = numbers[0];                 // Already an int; no unboxing.

Console.WriteLine(a + 5);           // 30
Console.WriteLine(b + 5);           // 30

List<int> also rejects adding a string at compile time. It still allocates its list object and backing storage; avoiding boxing does not mean avoiding every allocation. List<object> can be useful for mixed values, but consumers must handle the actual element types.

4. Python — integers are already objects

Complete program: main.py

Code

# Bind the name original to an integer object.
original = 25

# The list stores a reference to that integer object.
container = [original]

# Bind retrieved to the object referenced by the first list element.
# There is no separate C#-style unboxing step.
retrieved = container[0]
result = retrieved + 5

print(f"Original: {original}")
print(f"Retrieved: {retrieved}")
print(f"Result: {result}")

# Rebind original; do not modify the immutable integer object 25.
original = 100
print(f"Original after change: {original}")
print(f"Stored after change: {container[0]}")

Expected output

Output

Original: 25
Retrieved: 25
Result: 30
Original after change: 100
Stored after change: 25
StatementWhat it means
original = 25Binds original to an integer object whose value is 25.
container = [original]Creates a list containing a reference to that object. It does not copy the integer into a new C#-style box.
retrieved = container[0]Binds retrieved to the integer object referenced by the first list element.
result = retrieved + 5Computes an integer result and binds result to it.
original = 100Rebinds original to an integer object with value 100. The list still refers to the object with value 25.

Why rebinding does not change the stored value

Integers are immutable: their values cannot be changed in place. Before rebinding, original, retrieved, and the list element refer to the same integer object. After original = 100, only the association for original changes. This differs from C and C#, where the demonstrations retain earlier copies.

A useful check: immediately after retrieved = container[0], the expression retrieved is container[0] evaluates to True because retrieval gives the same object reference. Do not use is to compare numeric values in general; use == for value equality.

Runtime type errors are still possible

Independent example

container = ["25"]
retrieved = container[0]

# print(retrieved + 5)  # TypeError: str + int is not supported.

result = int(retrieved) + 5  # Convert the numeric text to an integer.
print(result)               # 30

The list can hold strings or integers, but the operation must make sense for the actual object. int("25") is a conversion from text, not unboxing. Invalid numeric text can raise ValueError.

Storage and performance trade-offs

  • The list requires storage for its container and element references.
  • In typical CPython execution, integer objects also carry runtime bookkeeping, and operations involve dynamic handling.
  • Inserting this integer into a list does not require allocating a new integer merely for insertion. Implementations can also reuse some integer objects.
  • Exact costs depend on the Python implementation and workload; the example alone cannot establish a speed ranking.

Python is dynamically typed: names can be rebound to different kinds of objects, but each object has a type that governs valid operations. This flexibility does not mean that types are absent.

Which approach would I choose?

  1. Embedded integer readings: choose C when the environment calls for predictable layouts and direct hardware integration. For a plain integer-only calculation, an int or int array may be enough; a wrapper should serve a real purpose.
  2. A typed application storing scores: choose C# with List<int> when all scores are integers. This keeps the collection convenient and typed while avoiding per-score boxing. Use object-based storage when the interface genuinely requires it.
  3. A quick data-processing script: choose Python when concise code and flexible data handling suit the task. Validate incoming data and measure performance if it becomes a requirement.

Reasoned conclusion: the best choice depends on the task, the environment, and the desired guarantees. C exposes representation choices, C# provides an explicit bridge between values and objects, and Python presents integers as objects from the beginning.

Keep performance claims tied to evidence

These examples teach semantics, not benchmarking. Console output, startup, build options, runtime optimization, and container differences affect timings. Measure a representative workload before claiming one implementation is faster.

6. Common misconceptions corrected

ClaimCorrection
“C structs perform built-in boxing.”The wrapper is manually defined. C has no corresponding built-in value-to-object boxing conversion.
“A void pointer boxes an int.”It can refer to existing storage without copying the value or recording a runtime type tag.
“An object variable changes the int into a different value.”Boxing preserves a copy of the value; the declared type of the receiving variable is object.
“Unboxing can directly widen a boxed int to long.”Unbox as int, then perform the numeric conversion.
“Python list retrieval is unboxing.”It retrieves a reference to an object already in the list.
“Using int() always means unboxing.”For example, int("25") converts text into an integer.
“Value types always live on the stack.”Storage depends on context; a value type can be a field inside a heap object.
“No boxing means no memory allocation.”A generic list still has its own storage; Python containers also require storage.
