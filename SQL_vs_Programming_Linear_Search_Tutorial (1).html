Linear Search vs SQL Server Queries

Programming Language Design

One small student dataset connects explicit search loops in C, Python, and C# to declarative SQL queries, indexes, and execution plans.

Learning objectives

  1. Review SELECT, FROM, and WHERE.
  2. Trace linear search in C, Python, and C#.
  3. Distinguish what result to retrieve from how to retrieve it.
  4. Explain table scans, index scans, index seeks, and the optimizer's role.
  5. Read a basic SQL Server execution plan and test an index.

1. One dataset, one question

Suppose a college maintains these student records:

0101AnaCS

Question: Find the student whose ID is 104. Expected result: Dev.

The data is intentionally small. The purpose is to compare language design and search behavior, not to benchmark performance.

2. Interactive linear search: trace each comparison

Linear search examines elements in sequence until it finds a match or reaches the end.

Change the target to 101, 105, or 999 and reset to compare best-case, last-position, and missing-record searches.

3. C: write the search steps explicitly

#include <stdio.h>

int main(void) {
    int ids[] = {101, 102, 103, 104, 105};
    const char *names[] = {"Ana", "Ben", "Cara", "Dev", "Eva"};
    int target = 104;
    int found = 0;

    for (int i = 0; i < 5; i++) {
        if (ids[i] == target) {
            printf("Found: %s\n", names[i]);
            found = 1;
            break;
        }
    }
    if (!found) printf("Student not found\n");
    return 0;
}

Trace: Compare 101 → 102 → 103 → 104; stop on the fourth comparison. The programmer specifies the loop, condition, and stopping rule.

4. Python: the same algorithm with shorter syntax

students = [
    (101, "Ana"), (102, "Ben"), (103, "Cara"),
    (104, "Dev"), (105, "Eva")
]
target = 104
found = False

for student_id, name in students:
    if student_id == target:
        print("Found:", name)
        found = True
        break

if not found:
    print("Student not found")

Trace: Python still checks records in order. The syntax changes, but the explicit algorithm is the same.

5. C#: the same explicit loop

using System;

class Program {
    static void Main() {
        int[] ids = {101, 102, 103, 104, 105};
        string[] names = {"Ana", "Ben", "Cara", "Dev", "Eva"};
        int target = 104;
        bool found = false;

        for (int i = 0; i < ids.Length; i++) {
            if (ids[i] == target) {
                Console.WriteLine("Found: " + names[i]);
                found = true;
                break;
            }
        }
        if (!found) Console.WriteLine("Student not found");
    }
}

Trace: The loop controls the search order, the condition checks equality, and break ends the search when the record is found.

6. SQL Server: describe the result, not the loop

Create the same records in SQL Server Management Studio (SSMS):

DROP TABLE IF EXISTS dbo.StudentDemo;
CREATE TABLE dbo.StudentDemo (
    StudentID INT NOT NULL,
    StudentName VARCHAR(40) NOT NULL,
    Major VARCHAR(40) NOT NULL
);

INSERT INTO dbo.StudentDemo (StudentID, StudentName, Major)
VALUES (101, 'Ana', 'CS'),
       (102, 'Ben', 'Math'),
       (103, 'Cara', 'CS'),
       (104, 'Dev', 'Physics'),
       (105, 'Eva', 'CS');

SELECT StudentID, StudentName
FROM dbo.StudentDemo
WHERE StudentID = 104;
SQL clauseMeaning
SELECT StudentID, StudentNameWhich columns should be returned?
FROM dbo.StudentDemoWhich table contains the data?
WHERE StudentID = 104Which rows qualify?

Result: 104 | Dev.

Important: SQL does not promise to check rows in insertion order. It describes the required result; SQL Server chooses a physical method. Without ORDER BY, result ordering is not guaranteed.

A table scan is conceptually similar to checking records one by one, but it is not identical to a source-code linear search loop. SQL Server uses pages, operators, parallelism, and other engine mechanisms.

8. SQL Server indexes: why the physical method can change

Without a suitable index

104

The engine may choose a Table Scan for a heap, or a Clustered Index Scan if the table has a clustered index.

With a useful index

Index on StudentID
101 · 102 · 103 · 104 → Dev · 105

An Index Seek may navigate to the matching key instead of scanning all entries.

Run this SQL to create a nonclustered index:

CREATE NONCLUSTERED INDEX IX_StudentDemo_StudentID
ON dbo.StudentDemo (StudentID);

SELECT StudentID, StudentName
FROM dbo.StudentDemo
WHERE StudentID = 104;

The optimizer may use an Index Seek plus a lookup for StudentName, or it may choose a scan. A five-row table is too small to reliably demonstrate a seek.

Covering-index option: For a larger experiment, an index with INCLUDE (StudentName) can provide the name directly from the index.

DROP INDEX IX_StudentDemo_StudentID ON dbo.StudentDemo;
CREATE NONCLUSTERED INDEX IX_StudentDemo_StudentID
ON dbo.StudentDemo (StudentID)
INCLUDE (StudentName);

Why not always seek? A scan can be cheaper for tiny tables, queries that return many rows, or situations where a seek would require many expensive lookups. Indexes also have storage and update costs.

9. Query optimizer: logical request vs physical execution plan

Logical request: “Return the ID and name of students with StudentID = 104.”

Optimizer: Estimates candidate plan costs using available indexes, statistics, and other information.

Physical plan: The actual operators selected to produce the rows, such as Table Scan, Index Scan, Index Seek, or Key Lookup.

SELECT / FROM / WHERE→Query optimizer→Execution plan→Result: Dev

View the execution plan in SSMS

  1. Open a new query window and run the setup script.
  2. Click Include Actual Execution Plan (or press Ctrl+M).
  3. Execute the SELECT statement.
  4. Open the Execution Plan tab and inspect the operator names.
  5. Compare the plan before and after adding the index.

Do not require a specific operator in this tiny example. Execution plans are cost-based and can vary with SQL Server version, statistics, row counts, and schema.
